## [Unreleased]

### Added
- **Jellyfin import in the setup wizard**: After the language step, the setup wizard asks whether to import from Jellyfin. If yes, you name Jellyfin's data folder, pick which Jellyfin user you are, check Jellyfin's libraries (correcting paths where this server mounts the media elsewhere; each is validated), and choose the other users to bring across, before the account step, whose name defaults to your Jellyfin user. On finish the server creates the libraries, scans them and then imports in the background: your Jellyfin user's watch data goes into your new account, and each other user gets an account with a one-time setup code, shown on the dashboard's import page where the wizard lands. Jellyfin passwords aren't carried over. Jellyfin's home videos become a Mixed library. If queueing the import fails after the account exists, the wizard lets you fix the import steps and retry, or finish without importing. The no-import path is unchanged.
- **Wizard import API**: `POST /Startup/JellyfinImport/Preview` reads a Jellyfin data folder for the wizard. It is open only while the server has no users (then 403, administrators included) and answers names, administrator flags, played-item counts, library names, types and paths, and item counts, never hashes, tokens or keys; it writes nothing; one runs at a time (409 for a concurrent one). `POST /JellyfinImport/Queue` (administrators, signed in) checks the libraries' folders and names and the source, then creates the libraries, scans them and imports; 202 with `LibraryIds`, 400 for a bad folder, name or source, 409 while an import is queued or running; its libraries are created in one transaction. `GET /JellyfinImport/Status` gains a `Scanning` stage. A queued import is kept in `jellyfin-import-queue.json` in the data folder: a restart during the scans resumes it, and a restart during the import is reported as failed instead of being lost or run twice.
- **Folder browse API**: `GET /Environment/DirectoryContents` and `GET /Environment/ParentPath` let a client browse the server's folders; they follow Jellyfin's API. DirectoryContents lists folders with `includeDirectories=true` and files (names only) with `includeFiles=true`, as Jellyfin does. It sorts by name, leaves out hidden entries and names that aren't UTF-8, returns at most 1,000 entries, and takes an optional `prefix` that filters names before the cap. At most 4 listings run at once (503 beyond that), and one that takes over 10 s answers 504. Like ValidatePath, both are open only while the server has no users, and to administrators after. `GET /Environment/Drives` now reports its entries as `Directory`, as Jellyfin does.
- **Folder path check**: `POST /Environment/ValidatePath` (Jellyfin's route) checks a folder with the same rules as creating a library. It answers 204, 404 when the path is not an existing folder, or 400 for other problems (not a full path, unreadable), with the reason in `Detail`. Like `/Startup/*`, it is open while the server has no users, then for administrators only.
- **PlaybackInfo by device profile**: `GET` and `POST /Items/{id}/PlaybackInfo`, the route Jellyfin's clients use to decide how to play an item, now answer; before, they answered 404. `POST` reads Jellyfin's PlaybackInfoDto body and its query parameters, which win over the body. With the body's `DeviceProfile`, or else the one the device posted to `/Sessions/Capabilities/Full`, each media source says whether the device can play it directly, stream it or must transcode it (`SupportsDirectPlay`, `SupportsDirectStream`, `SupportsTranscoding`) and why (`TranscodeReasons`), and gives an HLS `TranscodingUrl` that a player loads without an auth header, the default audio and subtitle streams, and how each subtitle stream is delivered: embedded, as an external WebVTT file at its `DeliveryUrl`, burned in, or in the HLS stream. For example, Chrome, whose profile has no 10-bit or 4:2:2 H.264, gets those files transcoded to 8-bit 4:2:0 and plays 8-bit H.264 directly. Audio items are decided by the profile's audio profiles and transcode to an audio-only HLS stream. `mediaSourceId` picks a version; when it names none, or the item has no sources, the answer is `{"MediaSources":[],"ErrorCode":"NoCompatibleStream"}`. `GET`, and `POST` without a profile, list the sources with every Supports flag set. `/Videos/{id}/PlaybackInfo` and `/Audio/{id}/PlaybackInfo` are unchanged.
- **Reverse sort in the library**: A toggle right after the library's sort select reverses the chosen sort, Name included, and replaces the Name (Z-A) option. The letter rail follows the reversed order. The sorts send jellyfin-web's lists, such as `DateCreated,SortName,ProductionYear`, so items that tie on the chosen field are ordered by name, then year.
- **Remembered audio and subtitle tracks**: The playback reports (`/Sessions/Playing`, `/Progress` and `/Stopped`) store the reported `AudioStreamIndex` and `SubtitleStreamIndex` per user and item (subtitle `-1` means off; a report without them keeps the stored ones), and `GET /Videos/{id}/PlaybackInfo` returns them as each media source's `DefaultAudioStreamIndex` and `DefaultSubtitleStreamIndex` while that source still has the stream, as Jellyfin does with its "remember" settings on. Each index is stored with the stream it named, taken from the source the report's `MediaSourceId` names (else the first source with a stream of that kind at that index), and is offered only where the stream at that index still has the same kind, codec, language, title, default and forced flags, and for an external subtitle the same file name. So when a file is replaced and an index now holds another track, such as a commentary or a dub, it isn't offered. Jellyfin apps read these defaults; the web player has no track choice yet.
- **Jellyfin import preview**: `POST /JellyfinImport/Preview` (administrators only) reads a Jellyfin data folder and reports what an import would do. It writes nothing.
  - **Finding the database**: `SourcePath` is the folder holding `jellyfin.db`, or a folder above it (`data/` or `data/data/`, as Docker images mount `/config`).
  - **Layouts**: both Jellyfin database layouts are read, the current one in `jellyfin.db` and the older `library.db`.
  - **Read-only**: a database file and its `-wal` of up to 256 MiB together are read into memory once, with the committed frames of the `-wal` applied by Rustyfin, and queried there; that takes memory of about twice their size. Bigger ones, of any size, are copied into a private folder in Rustyfin's data folder (`jellyfin-import-copy`, mode 0700), opened read-only there with SQLite applying the copied `-wal`, and removed once read, so the data folder needs room for the largest database. A copy starts only when the data folder's disk has room for it with 1 GiB to spare (else the source is refused with the space needed and free), and holds at most the sizes measured before it; a file that grows while it is copied counts as changed. Either way the import sees one state while Jellyfin writes and creates nothing in the source folder (no `-shm`); files that change during five tries in a row are a bad source, and so is a database or `-wal` that is not a regular file, such as a FIFO or a link to a device. Every table the import reads must be a plain table: a view, a virtual table or a table with generated columns in its place is a bad source, found before any row is read. So is a damaged table, such as one whose pages repeat: each is checked with SQLite's `quick_check` before it is read — its b-trees are walked first, so a tree too deep or one that shares pages between tables is refused before that check can recurse into it — and a crafted schema that would make reading it spin is cut off, and one built to blow up when SQLite compiles it is refused first, never compiled, or stopped by a cap on the size of a compiled statement. Memory use still grows with the size of the schema itself. Password hashes, API keys and device tables are never queried.
  - **The report**:
    - the suggested path pairs, from Jellyfin's library links to Rustyfin's library paths, which a request can replace (a link file, `.mblink`, holds one path, so one over 64 KiB is a bad source, as is a source whose links top 1 MiB of text in total);
    - the users, to match, create or skip, with the former administrators marked. A picked user whose name matches one existing account (case-insensitively, an exact-case match first) gets it as `SuggestedMatch` (its id and name; `IsAdministrator`; `CreatedAt`; `LastLoginDate`, null when it has never signed in; `SetupCodePending` while it still holds an unused setup code from an import, the only record that an import created it; and `OtherCaseNames`, the other accounts whose names sign-in counts as the same name, such as other cases, ß and ss, or composed and decomposed accents), but the user's data goes into that account only when the admin confirms the pairing: the request's `ConfirmedMatches` lists it by the Jellyfin user's id and the account's id, and it is still the suggestion when the run starts. Unconfirmed, the user is skipped (`NotConfirmed`), neither created nor imported; a confirmation that names any other account is refused (`ConfirmedOtherAccount`), so no rename can send anyone's data to an account the admin didn't confirm. A name that matches several accounts is skipped, as before, and a user with no match is created, unless the request confirms a pairing for them;
    - the items matched by path, matched by TMDB or TVDB id (seasons and episodes through their series), and unmatched, with up to 200 unmatched items that hold watch data.
- **Jellyfin import run**: `POST /JellyfinImport/Run` (administrators only) starts an import with the preview's request and answers 202 while it runs in the background; the source is read first, so a bad source gets the preview's 400, and a second run while one runs gets 409. `GET /JellyfinImport/Status` reports the state (`Idle`, `Running`, `Completed` or `Failed`), the stage and its progress, and the report or the error.
  - **New users**: each picked Jellyfin user without a Rustyfin match becomes a Rustyfin user with default settings, no administrator rights and no usable password, and gets a one-time code. Only an argon2 hash of the code is stored; the first status answer that shows the finished run carries the codes, later answers don't, and no log line holds one.
  - **Re-runs**: users an earlier run created are existing accounts by then, so running an import again creates no one whose earlier account still has their name, and their data goes in again only when the admin confirms them again. Nothing records earlier confirmations.
  - **Import into my account**: Preview and Run take `IntoMyAccount`, a Jellyfin user id whose watch data, track choices and favorites go into the calling administrator's own account, whatever the names, so an owner who was `admin` in Jellyfin brings their own history over. The account always comes from the request's sign-in, never from the body, so no one else can be pointed at another person's account. The user's row is a `Match` into the caller with `MatchKind` `IntoMyAccount` and the caller's account facts as `TargetAccount`; no account is created and no code is issued, and the caller's rights and password stay. A Jellyfin user whose name matches the caller is then skipped (`AccountTakenByIntoMyAccount`); everyone else is handled as before. A pick that isn't in the source, is missing from `UserIds`, or is confirmed with another account in `ConfirmedMatches` is a 400, and so is the field from the configured API key, which has no account. Nothing is recorded, so a re-run needs the field again. On the import page, an "Import into my account" select above the users picks one, changes the row's action at once, and a hint points to it when none of the selected Jellyfin users is matched to the admin's account by name. A finished run's list names the account when another administrator reads it.
  - **Watch data**: the preview counts, and a run imports, each picked user's played state, play count, resume position, last-played date, favorite, rating and likes on the matched items, from both layouts (in the older one a row applies to every item with its user-data key; only the first row of a key and user counts, and a file that gives more watch data than its items and rows together is a bad source). Several Jellyfin rows for one item count as the newest. Each row merges with Rustyfin's own: played and favorite if either side says so, the larger play count, the later date, the resume position and track choices from the side that played last, and Rustyfin's rating and likes when it has them. Jellyfin's rating is a decimal from 0 to 10 and Rustyfin's a whole number, so it is rounded half away from zero. A run reads, merges and writes each Rustyfin user's rows in one write transaction, so progress saved during the run is merged, not overwritten. The report counts the rows as imported, unchanged or unmatched; running again with nothing changed in Jellyfin writes nothing.
  - **Track choices**: a row's last audio and subtitle track becomes the stream of the Rustyfin file at the Jellyfin item's path with the same kind, codec, default and forced flags, and language and title where both sides know them; external subtitles also need the same file name, and equal tracks are told apart by their order among the embedded ones. A choice without exactly one such stream is dropped and counted, as is every audio and subtitle choice of an entry with no Rustyfin file at its path, such as an old file matched by its ids; subtitles off (`-1`) stays off.
  - **First sign-in**: a created user's first sign-in is `POST /Users/AuthenticateWithSetupCode` with `Username`, `Code` and `NewPw`. It sets the new password, uses up the code and answers like `AuthenticateByName`; it counts against the login rate limit. `AuthenticateByName` with the code as the password still fails with the usual 401 and starts no session, but the answer carries `X-Rustyfin-Setup-Required: true` so a client can offer to choose a new password; other apps see a failed sign-in. Administrators list the users who still have a code with `GET /JellyfinImport/PendingUsers` and replace a user's code with `POST /JellyfinImport/Users/{userId}/SetupCode`, the only answer that shows the new code. Any other password change ends the code, and a disabled user's code doesn't work. Each code check, on either endpoint, runs one argon2 verification whether or not the user exists, has a code or is enabled, so the answer time doesn't tell who has a code.
  - **Metadata**: a run also imports the matched items' metadata from both layouts: name, sort name, original title, overview, tagline, official, community and critic ratings, premiere and end dates, production year, genres, tags, studios and the TMDb, TVDB and IMDb ids; the people with their role, kind and order, one per credit even when Jellyfin lists a person's id twice (a person whose name is longer than 1 KiB is left out, and a kind longer than 64 bytes is dropped); and the images of the items and their people (primary, art, backdrop, banner, logo, thumb, disc and screenshot), each person's images added once however many credits name them. `MetadataMode` is `FillEmpty` (the default: only values Rustyfin lacks), `Replace` (every value Jellyfin has that differs, except the TMDb and TVDB ids: they decide what matches, so they only fill empty ones in both modes) or `None`. A value Jellyfin lacks never clears Rustyfin's, and items or fields locked in Rustyfin keep theirs; Jellyfin's own locks are not read. Images are found through the path pairs, or for `%MetadataPath%` and `%AppDataPath%` under Jellyfin's program data folder; when that folder holds `metadata`, a pair from the prefix Jellyfin's image paths share is suggested. JPEG, PNG, WebP and GIF files of up to 32 MiB inside the paired folder are copied into `images/` in Rustyfin's data folder, with Jellyfin's size and blurhash; other images count as missing, and nothing is fetched from the network. A copy reads the file that was checked: a file replaced or linked in after its check (another inode, size or time) is not copied. The report's `Metadata` counts the changed items, fields, people and images, the missing images and the locked items; the preview counts the same and copies nothing. When Jellyfin holds several entries of one item, such as an old file of a movie beside the current one, the metadata comes from the entry matched by path, and the TMDb and TVDB ids a run writes already count for its own matching, so a second run imports nothing more. A later library scan keeps the imported values. `GET /Items/{id}` also returns `OriginalTitle`, `CriticRating`, the IMDb id, `LockData` and `LockedFields`; people come in their order, with their kind as `Type` and a `PrimaryImageTag` when they have an image, which `/Items/{personId}/Images/Primary` serves.
  - **Import page**: the web dashboard's last tab, "Jellyfin import", explains how to mount the Jellyfin folder read-only in Docker. It previews a folder (the layout found, editable path pairs, unpaired library folders, each user's action with a checkbox, under a name match an unticked "Import into the existing account …" box whose tick Run sends as a confirmation and which changes the row's action at once, with the account's facts beside it and a warning when other accounts differ from it only in case, the counts and unmatched samples) and runs the import with a progress bar. A "Metadata" select picks filling empty fields (the default), replacing with Jellyfin's (its help says Rustyfin's TMDb and TVDB ids stay) or no metadata, and the preview and run results show the metadata counts. A finished run shows the new users' codes once, with a copy button, and names the new users who were Jellyfin administrators. The tab also lists the users still waiting for their first sign-in, each with a "New code" button. Codes stay in the page: never in storage, the URL or the console.
  - **Choose a new password**: signing in to the web client with a code opens a form for the new password, which then signs the user in; Back returns to the sign-in form.
- **Web client translations**: The web client is localized with i18next, with English and German translations in `crates/rustyfin-web/src/translations/` (one JSON file per language, English as the source). The display language follows the browser and can be changed in the setup wizard and in the user settings; picking it in the wizard switches the UI immediately. Previously the UI was German only.
- **OpenID Connect settings**: `GET` and `POST /Auth/Oidc/Settings` (administrators) hold the settings of one OpenID Connect sign-in provider (migration 050). A save merges the fields sent. A save that turns OIDC on checks the URLs, then fetches the provider's discovery document and keys, and answers 400 with a `Detail` saying what is wrong. The client secret is write-only: answers show only `HasClientSecret`. `GET /Auth/Oidc/Info` (public) tells the sign-in page whether OIDC is on and what the button says.
- **Password sign-in switch**: `AllowPasswordSignIn` in the OIDC settings, on by default. While it is off, a non-administrator with the right password gets 403 at `/Users/AuthenticateByName`, `/Users/ForgotPassword` issues them no PIN, and resetting their password by PIN answers 403. Administrators are not affected, unless their rights come from the admin group.
  - The switch covers the one-time codes of users created by a Jellyfin import too. While it is off, `POST /Users/AuthenticateWithSetupCode` answers such a user's right code with 403 and leaves the code unused, and `AuthenticateByName` with the code as the password sends no `X-Rustyfin-Setup-Required` header, so the web client doesn't offer the new-password form. The code works again once password sign-in is back on.
- **OpenID Connect sign-in**: `POST /Auth/Oidc/Start` answers with the provider's authorization URL (the authorization-code flow with PKCE, `state` and `nonce`) and sets an HttpOnly flow cookie that lasts 10 minutes. `GET /Auth/Oidc/Callback` exchanges the code, checks the ID token (signature, algorithm, issuer, audience, `azp`, expiry, nonce) and sends the browser back to the sign-in page, or to `#login/oidc-error/<code>` when it refuses. `POST /Auth/Oidc/Complete` then hands out the session once, like a password sign-in. A first sign-in creates a user with no password, and is refused when a user already has that name (names match in any letter case and Unicode compatibility form, such as `STRAUSS` and `Strauß`, or fullwidth letters; accents count), also when two first sign-ins with one name arrive together: usernames are never matched, so that person signs in with their password and links the provider from the profile, or asks an administrator. When an allowed group is set, only its members get in. The provider's discovery document is cached for an hour, and its keys are fetched again once for a token signed with an unknown key.
- **OpenID Connect links**: `POST /Auth/Oidc/Link` links the signed-in user's own account to a provider account, administrators included, and sends the browser back to `#settings/oidc-linked`. `GET /Auth/Oidc/Accounts` (administrators) and `GET /Auth/Oidc/Accounts/{userId}` (the user or an administrator) show each account's link, whether it has a password and whether it can be unlinked. `DELETE /Auth/Oidc/Accounts/{userId}/Link` removes a link. Users can remove their own link only while they can still sign in with a password; otherwise they get 409 with the reason. Administrators can remove anyone's link.
- **Admin rights from a provider group**: With `AdminGroup` set, a member becomes an administrator at their next OIDC sign-in or link. Rights the group gave go when the user leaves the group, when `AdminGroup` is cleared, or when the account's link is removed, by the user or by an administrator. A sign-in through the provider that is still under way when the link goes is refused, with no session and no rights. The owner and the last enabled administrator keep their rights, and a warning is logged instead. Rights given by hand are never taken away, and changing `IsAdministrator` in `POST /Users/{id}/Policy` makes the rights hand-given; sending the current value again, as clients that send back the whole policy do, leaves them group-given.
- **OpenID Connect in the web client**: While OIDC is on, the sign-in page shows a button with the configured label. It goes to the provider, and the return to `#login/oidc` finishes the sign-in. A refused sign-in shows a message for its reason, and a non-administrator who signs in with a password while password sign-in is off is told so. The profile has a Single sign-on card that links the account, shows the link and removes it, or says why it can't be removed. A user without a password can set one without entering a current password.
- **OpenID Connect admin pages**: The dashboard has a Sign-in tab with every OIDC setting. The callback URL is read-only with a Copy button, the public URL starts as the browser's address, and the client secret is write-only, with an option to remove a saved one. A refused save shows the server's message. Warnings explain when group changes apply, and that with password sign-in off only administrators given rights by hand still sign in with a password. The users list shows each user's provider link with a Remove button, and marks admin rights that come from the admin group.
- **Library scan progress**: Every library scan reports its progress on the socket (`/socket`) to every signed-in user: `RefreshProgress` frames with the library id, a whole percent and a `State`: `"0"` and `"Queued"` while the scan waits its turn, each higher percent with `"Active"` as its probes (and, with a metadata provider configured, the metadata refresh of new items) finish, and `"100"` and `"Idle"` when it ends. A new socket first gets one frame per scan in progress. This covers scans started from the web client, Scan All and the scheduler, including its scan 60 s after start. A web scan's `ScheduledTaskCompleted` now comes when the scan has ended, after its probes, instead of when the scan request returns. A library is scanned once per queued scan: a second request for a library whose scan is still queued joins that scan and returns at once, without task events of its own, except that the first request to join a scan the scheduler has claimed sends that scan's `ScheduledTaskStarted`, and its `ScheduledTaskCompleted` when it ends, since the scheduler sends neither; a manual scan of a library that Scan All or the scheduler has queued but not reached takes it over, so they skip it.
- **Rescan of reported folders**: A client or an *arr app can now report a changed file or folder, and Rustyfin rescans only the library folder that holds it. A report queues the top-level folder of the library path that holds it (or the files directly in the library path) and reads nothing on disk, so a hung mount can't hold up the request. The folder is rescanned under its name on disk, so a path reported in another case on a mount that ignores case adds no second item. The folder is rescanned once `LibraryMonitorDelay` seconds (server configuration, 60 by default) have passed without another report for it. More than 50 queued folders of one library become one scan of the whole library, which starts `LibraryMonitorDelay` seconds after it was queued, however many reports follow. Before, a change showed only after the next scan of the whole library, and these endpoints answered 404. The reports come from an administrator or the API key (`RUSTYFIN_API_KEY`), at most 10,000 paths per request (a larger request gets 413 and reports none), through:
  - `POST /Library/Media/Updated`, Jellyfin's endpoint, which the Emby / Jellyfin connection of Sonarr and Radarr calls after an import. `GET /Items` now also reads `recursive`, `fields` and `years` in lower camel case, as these apps send them to look up the library's items.
  - `POST` or `PUT /Library/Media/Webhook`, for the Webhook connection of Sonarr, Radarr and Lidarr: imports, upgrades, renames and deletes report the files and folders they touch. Repeated `from` and `to` pairs in its URL map the apps' paths to the server's, for example `?api_key=…&from=/tv&to=/mnt/media/TV`.
- **Audio and subtitle menus in the player**: the audio and subtitle tracks of an item can be chosen in the player, starting from the defaults: the stream the server marks as default audio, else the first; for subtitles Jellyfin's Default mode (external first, then forced in the audio's language, forced, default; Off when none qualifies). Changing the audio, or choosing a picture subtitle (PGS, DVD, VobSub, DVB), restarts the transcode at the current position; a text subtitle is added as WebVTT without a restart. Playback reports carry the media source and the chosen audio and subtitle indexes.
- **Real-time library monitoring**: Rustyfin now notices added, changed, renamed and removed files in a library by itself and rescans only the folder that changed, through the same queue and `LibraryMonitorDelay` as reported folders, so a change shows without a scan. Each library path gets one method, which the log names with the path's filesystem and folder count, and the interval when it is polled. Folders on a local disk are watched with inotify on Linux. Network shares and every filesystem not known to be local (NFS, SMB, sshfs and other FUSE mounts among them), and every path on other systems, are polled instead: every `LibraryMonitorPollInterval` seconds (server configuration, 60 by default) Rustyfin compares each folder's modified time. A symlinked folder counts as being on its target's filesystem, and `RUSTYFIN_MONITOR_FORCE_POLL=1` polls every path. A file still being copied is rescanned once more when it is complete, and a folder copied into a folder meanwhile is found even when the copy tool puts the outer folder's modified time back. When the kernel runs out of inotify watches or instances, or Rustyfin out of open files, the path is polled, and the log names the limit to raise once: `fs.inotify.max_user_watches`, `fs.inotify.max_user_instances`, or the open file limit. Raise the open file limit and restart Rustyfin (`ulimit -n`, systemd's `LimitNOFILE=`, Docker's `--ulimit nofile=`), or raise it live with `prlimit --pid`. Once a limit is raised while Rustyfin runs, `SIGHUP` or the next library change watches the path again. Until a limit changes, the path keeps polling with its last state, also when other processes free inotify watches or instances (both limits are per user) or when Rustyfin frees open files. On Linux, a share mounted on, above or inside a watched library path while Rustyfin runs sets the path up again, with the method of the share's filesystem, and so does a share mounted again at the target of a symlinked folder in it. A polled path keeps its last state instead: when its share goes away and comes back, what was added, changed or removed meanwhile is reported at the next poll. It is set up again only when it can be watched now or when a share inside it went away, and never for an automount. When a share goes away from a library path or from inside it, nothing is reported for its folders. Rustyfin reads a burst of mount changes about once a second, and when the mount table or the library list can't be read, it tries again after 1 s, 2 s, 4 s and so on, up to a minute. Rustyfin exits at once even while a poll waits on a hard-mounted NFS share that stopped answering. Each library has an **Enable real-time monitoring** setting (`EnableRealtimeMonitor` in its options, on by default, also for libraries saved before), in the add-library dialog and as a column of the libraries table in the Server Dashboard. Switching it, adding or removing a library, removing one of its paths, and changing `LibraryMonitorPollInterval` (also through `SIGHUP`) take effect at once; switching it off also stops a setup still walking the library's folders. Changes made while monitoring is off show after the next scan. Reports through `/Library/Media/Updated` and the Webhook work whatever the setting.
- **User roles in the dashboard**: The Users tab has an Admin and a Disabled checkbox for each user. `POST /Users/{id}/Policy` also takes `IsDisabled`. A disabled user can't sign in. Disabling deletes the user's tokens, sessions and devices at once, so they leave the sessions list, an open websocket closes within 5 s, and none of them comes back when the account is enabled again. As in Jellyfin, an administrator can't be disabled, not even in the request that removes the rights: remove them first, then disable. A disabled account becomes an administrator only in the request that enables it, and the last enabled administrator stays one. The owner's role and access can't be changed, and no administrator can demote or disable their own account. The dashboard locks every box the server would refuse, with the reason. A change takes effect on the user's next request, and an open websocket follows within 5 s. Rights the provider's admin group gave and an administrator removes come back at the user's next single sign-on sign-in while they are in the group, and the dashboard says so. User answers carry `IsOwner` and `IsDisabled`.

### Changed
- **Changing your own password**: `POST /Users/{userId}/Password` needs a correct `CurrentPw` from everyone who has a password, including administrators changing their own; an administrator changing another user's password still needs none. A user without a password, as an OIDC sign-in creates, sets a first one without `CurrentPw`. Such a user gets 401 at password sign-in.
- **User names in any letter case**: Password sign-in (`POST /Users/AuthenticateByName`), `/Users/ForgotPassword` and resetting a password by PIN find an account by its name in any letter case and Unicode compatibility form, as Jellyfin does: the exact name first, else the one account whose name matches. When several accounts match and none exactly, the sign-in fails as with a wrong password. `POST /Users/New` and renames refuse a name that matches another account's with 400 "user already exists"; users may still change the case of their own name. A name longer than 255 UTF-16 code units, whether entered or kept from an older server, matches only an exactly equal name, and a first sign-in through single sign-on is refused when the provider sends a longer username (`no_username`). Redeeming a reset PIN removes its file, whatever spelling the reset was asked with, also when the reset was asked before the upgrade. Before, names matched only exactly, and a rename to another user's exact name answered 500. Accounts whose names already differ only in case keep signing in with their exact names.
  - A one-time code from a Jellyfin import finds its account the same way, both at `POST /Users/AuthenticateWithSetupCode` and when it is typed as the password.
- **User policy and public users**: `POST /Users/{id}/Policy` answers 404 for an unknown user whatever the body; before, a body without `IsAdministrator` got 200. `GET /Users/Public` leaves out disabled users, as Jellyfin does. When no enabled administrator is left, the startup log's recovery hint now sends `{"IsAdministrator": true, "IsDisabled": false}` to the Policy endpoint, which can enable a disabled account too, instead of sending operators to the database for that.
- **pnpm for the web client**: `crates/rustyfin-web` uses pnpm instead of npm. `package.json` pins the version in `packageManager` (Corepack and `pnpm/action-setup` read it), and `pnpm-lock.yaml` replaces `package-lock.json` with the same dependency versions. The Dockerfile, the release workflow, `build.sh`, `start.sh` and the README use pnpm.
- **CI on the image's Debian, building once**: The CI check job runs in the `rust:1-trixie` container, on the Debian release of the Docker image, with the image's `ffmpeg` package, so the tests that need ffmpeg and ffprobe run instead of skipping. Cargo runs as a user that isn't root, since the tests that lock a folder skip themselves under root. The check job builds the release binary once, a parallel job builds the web client with pnpm, and the Docker job puts both into the image with the Dockerfile's new `prebuilt` target instead of compiling everything again. A plain `docker build .` still builds everything from source.
- **DLNA server off by default**: The DLNA server, its `/dlna/*` endpoints and its SSDP announcements, runs only when `EnableDlnaServer` is on in the server configuration. Before, it always ran and listed the libraries to anyone on the network without a sign-in. An administrator turns it on with `POST /System/Configuration`; the `/dlna/*` endpoints follow the setting at once, and SSDP starts at the next server start.
- **Letter rail in the library**: The library page's letter bar is now a vertical rail at the right edge, like Jellyfin's alphabet picker. It stays in view while the list scrolls and highlights the letter of the first title at the top of the view. A click scrolls to that letter's first title and filters nothing; the first entry (`#`, or `Z` in Name Z-A, where the rail runs from Z to A) goes back to the top. It shows for the name sorts, as the bar did. Before, the bar scrolled away with the list and never marked the current letter.
- **Access tokens survive restarts**: Access tokens are now opaque values stored server-side, one per device, instead of self-contained JWTs signed with a per-start secret. A restart no longer logs anyone out, and the server id is stable across restarts (persisted to `<data>/server_id`). `RUSTYFIN_SECRET` is now ignored (with a one-time startup notice). **Upgrade note:** tokens issued by an older build stop working once, at the upgrade — every client signs in again after updating.
- **Stricter login rate limit**: Only the login, forgot-password and reset endpoints are rate-limited. Before, one budget of 500 requests per 60 s per client IP covered every route, so a remote client scrolling a library grid got 429 for its thumbnails within seconds. These endpoints now allow 10 requests per 60 seconds per client IP by default, tunable with `RUSTYFIN_RATE_LIMIT` and `RUSTYFIN_RATE_WINDOW` (`0` disables). `X-Forwarded-For` is trusted only from a proxy listed in the new `RUSTYFIN_KNOWN_PROXIES` (comma-separated IPs or CIDRs; loopback only when listed); otherwise the connecting peer address is used, so a spoofed header can no longer claim the loopback exemption or rotate past the limit.

Movies and episodes get their media sources, streams and chapters back at the next scan, images come back at the next metadata refresh unless they were uploaded through the API, and episodes get their segments back at the next intro detection. Playlist and collection entries don't come back.
  - Filters drop a year or rating once no item has it.
  - Search forgets the old names that refreshes left behind.
- **Metadata refresh keeps newer changes**: A metadata refresh writes only the fields it changes, and each only while it still holds the value the refresh read. Before, it saved every field of the copy it had read, so a rename or year from a rescan, a path or runtime from the probe, or fields the Jellyfin import wrote while the refresh ran were set back. A later metadata source also no longer empties fields an earlier one filled. The first source that fills a field keeps it: the .nfo, then TMDb, then OMDb. Before, the last one's value won.
- **Large imports and rating counts**: The filter counts find an item's rating through a new index instead of reading every item. An import that writes 20,000 items in one transaction held the database for more than the 30 s other writes wait, so they could fail with "database is locked"; it now takes a few seconds.
- **Genre, studio and year lists**: `GET /Genres`, `/MusicGenres`, `/Studios` and `/Years` return a `QueryResult` of `Genre`, `MusicGenre`, `Studio` and `Year` items. Names are trimmed and listed once whatever their case and accents, under their most common spelling, and each item's id is built from its type and its name folded much as Jellyfin folds it (case and accents; Rustyfin also composes NFC), so it is the same in every list and after a rescan. The lists take `ParentId`, `IncludeItemTypes`, `ExcludeItemTypes`, `MediaTypes`, `SearchTerm`, `NameStartsWith`, `NameStartsWithOrGreater`, `NameLessThan`, `SortOrder`, `StartIndex`, `Limit`, `EnableTotalRecordCount`, `Fields=ItemCounts` and `UserId`, and a music library as `ParentId` turns `/Genres` into the music genres, as in Jellyfin. `GET /Genres/{name}`, `/MusicGenres/{name}`, `/Studios/{name}` and `/Years/{year}` return one item, or 404 when no item of that kind has it. `GET /Items` applies `GenreIds` and `StudioIds`, and an item's `GenreItems` and a single item's `Studios` carry the ids that these lists use. Before, `/Genres` failed with a 500 on the genres stored since migration 014, `/Studios` was always empty, `/MusicGenres` and `/Years` didn't exist, `/Genres/{name}` listed the song genres that contained the name, with new random ids on every call, `/Genres/Music` hid a genre named Music, `/Studios/{name}` failed with a 500, `/Items` ignored `GenreIds` and `StudioIds`, so a genre page listed the whole library, and item genre and studio ids were slugs such as `action` and `studio-pixar`.
- **Favourites, played state and ratings on an unknown id**: `POST` and `DELETE /Users/{userId}/FavoriteItems/{itemId}` and `/Users/{userId}/PlayedItems/{itemId}`, `PUT /Users/{userId}/Items/{itemId}/Rating`, and `DELETE /UserFavoriteItems/{itemId}` and `/UserPlayedItems/{itemId}` answer 404 when the id is not a media item, such as the id of a genre or studio from the lists above, as Jellyfin does. Before, the first five failed with a 500 and logged an error, and the two short routes answered 200 and changed nothing.
- **Playback reports on an id that isn't a media item**: `POST /Sessions/Playing`, `/Sessions/Playing/Progress` and `/Sessions/Playing/Stopped` succeed and store nothing when the id is not a media item, such as a genre, studio or library id, and the `SessionChanged` event they send names no now-playing item, as Jellyfin does for an id it can't find. `POST /Playstate/LastActivityDate` skips such ids and updates the rest. Before, these failed with a 500 and logged an error (a progress report only when it carried a position or a track index).
- **Jellyfin credentials**: A request can carry its token in `Authorization: MediaBrowser …, Token="…"` (scheme `MediaBrowser` or `Emby`, in any case), in the same form in `X-Emby-Authorization`, or in the `ApiKey` query parameter, as Jellyfin's apps send it, with values URL-decoded the way Jellyfin decodes them. The first source that holds a token decides, so an invalid token is refused even when a later source holds a valid one. Before, these requests got 401, and so did `rustyfin-cli` commands that need a sign-in; they now authenticate. The API key (`RUSTYFIN_API_KEY`) matches `api_key` and a `MediaBrowser` `Token` either as typed or URL-decoded, so a key that holds `+` or `%` keeps working in the Webhook URLs and Emby / Jellyfin connections of Sonarr, Radarr and Lidarr, which send it as typed. A blank token now counts as absent, so the next source decides, where before it got 401, and `api_key` now matches in any case, such as `API_KEY=`.
- **Resumed and seeked transcodes**: `GET /Videos/{id}/main.m3u8` reads `StartTimeTicks`, which Universal already forwards, and starts ffmpeg there (`-ss` on the input, plus `-copypriorss 0` when a stream is copied), so the playlist's time 0 is that point. Before, every transcode started at 0:00 and a resume played from the beginning. A playlist request of a play session (else device) whose transcode has other tracks, another start or other limits replaces that transcode; before, it got the old one. A seek or track change in the last moments of a transcode ends the playback; before, the player waited at the end.
- **Stream languages and titles**: The probe reads a stream's language and title from ffprobe's `tags`, where ffprobe puts them, so audio and subtitle tracks get them in `MediaStreams`. Before, every stream had neither. Files probed before keep empty values until they are probed again.
- **Track labels of files probed before**: The first library scan after this update reads every stored video and audio file again, once, so the audio and subtitle tracks of files probed before get their language and title. Any scan does it: Scan, Scan All, the scheduled and startup scans, and a library monitor rescan of the file's folder. On a large library it takes about 30 minutes to 2 hours, most of it spent reading the files from disk. Other scans wait for it, so files downloaded while it runs appear only after it ends. A player open on an item while the scan reads it again may need a reload. Later scans read a file again only when it changes. A scan stopped part way keeps what it read, and the next scan reads the rest. An unchanged file that ffprobe can no longer read keeps its tracks as they were; when ffprobe does not run, a scan reads no file again and logs a warning. Before, a scan skipped unchanged files, so their tracks kept empty values.
- **Forced subtitles**: A subtitle track in a video file counts as forced only when the file flags it as forced, as in Jellyfin. A title that says "forced" no longer counts; the title still shows in the track menus. The first scan after this update applies this to the tracks already stored.
- **Item details after a file is read again**: `GET /Items/{id}` serves its cached copy of an item only while the item's sources are the ones it cached. A scan that reads a file again replaces them, so the details show the new tracks and source at once. Before, a music track's details could show the old tracks and a source that no longer existed for up to five minutes, and playing that source failed with 404.
- **Audio track in transcodes**: `AudioStreamIndex` on `GET /Videos/{id}/main.m3u8` picks the stream with that index, the absolute index Jellyfin clients send, and the output keeps the video. Before, it was read as a place among the audio streams, and the output had no video.
- **Burned-in subtitles**: With `SubtitleMethod=Encode` (or `BurnSubtitles=true`), `GET /Videos/{id}/main.m3u8` burns in the subtitle stream `SubtitleStreamIndex` names: picture subtitles (PGS, VobSub, DVB) are overlaid on the video, and text subtitles are drawn from the right stream, whatever characters the file's path holds. `-1` for `AudioStreamIndex` or `SubtitleStreamIndex` means the default audio or no subtitle. Before, a picture subtitle failed the transcode, a text subtitle of a file whose path held `'` or `:` failed the transcode, a text subtitle's index was read as a place among the subtitle streams, and `-1` failed the request with a 400.
- **Text subtitles for players**: `GET /Videos/{id}/{mediaSourceId}/Subtitles/{index}/Stream.vtt`, where Jellyfin clients load subtitles, serves an embedded or external text subtitle (SubRip, ASS/SSA, WebVTT, mov_text) as WebVTT, converted by ffmpeg and cached under the data dir, one file per subtitle (removed when unread for 30 days, or the oldest first past 512 MiB in all). With `/{startTicks}/` before `Stream.vtt`, the cues that end by `startTicks` are dropped and the rest move back by it, for a transcode that starts there. An external file that is not UTF-8 is read as Windows-1252. A picture subtitle gets a 400, since players burn it in. At most two conversions run at once, one per subtitle, which later requests for it wait for; one stops after 10 minutes; a subtitle file or WebVTT text over 32 MiB gets 413. Before, these routes answered 404.
- **Chosen tracks on Universal and PlaybackInfo**: `GET /Videos/{id}/Universal` sends an `AudioStreamIndex` other than the file's default audio, or a picture subtitle in `SubtitleStreamIndex`, to an HLS transcode and passes both indexes on to it, burning in the picture subtitle, since a browser plays only a file's default audio and draws no picture subtitle. `GET /Videos/{id}/PlaybackInfo` lists the subtitle files beside a video as external streams, numbered after its own streams. Before, Universal ignored both indexes and direct-played the file, and PlaybackInfo listed no external subtitles.
- **Player progress bar**: the web player measures the elapsed time, the total time and the bar against the item's runtime from the first frame, and counts a transcode's time from the point it started at, which playback reports send too. A resume or a seek outside the transcoded part starts the transcode at that point through `StartTimeTicks`, after a 400 ms pause for further seeks, and stops the old transcode; a seek inside it moves in place. Before, the bar measured a transcode against the part transcoded so far, so it ran ahead to the end and snapped back, and a resumed transcode started hls.js past the part transcoded so far.
- **Transcodes stop with the player**: the web player stops its transcode (`DELETE /Videos/ActiveEncodings`) when it closes, when another item starts, at the end and when the page is left. Before, a transcode ran on and kept its files until it had been idle for 30 minutes. For a minute after a stop, a playlist request of that PlaySessionId gets 404, so a request still on its way can't start the transcode again.
- **Configuration values that don't fit**: `POST /System/Configuration/{key}` answers 400, naming the key, when the value doesn't fit the setting, such as `"abc"` or `-1` for `LibraryMonitorPollInterval`, and leaves the configuration as it was. Before, it answered 500.
- **Sort order of item lists**: `GET /Items` and `GET /Users/{userId}/Items` order by each `SortBy` key in turn and read `SortBy` and `SortOrder` as Jellyfin's comma lists: each key takes the order at its position, the rest take the first order. Ties go as in Jellyfin: a leading `SortName` brings `Name` along in its direction, and `SortName` ascending follows when no name key is given. The item id comes last, so pages are stable and a reversed list is the exact reverse. Release date falls back to January 1 of the production year, as in Jellyfin. A key that repeats one already in the list counts once, at its first position and in its order, as in Jellyfin, so a list of any length sorts. Before, the whole `SortBy` value picked one column with no tie-break. On a library without metadata, where every item lacks a release date and a rating, the Release date and Rating sorts therefore came out in no useful order, and lists such as `DateCreated,SortName` fell back to the name.
- **Date added**: A scan dates each new item the way Jellyfin does on Linux: by its path's creation time, which .NET reads there as the older of the modification and status-change times. A file that is a symlink takes the times of its final target, as Jellyfin resolves one; a folder link keeps its own. A movie takes the date of its video file; a series, season, artist or album the date of its folder; an episode, track or photo the date of its file. The Date added sort and the recently added lists follow these dates. Before, every item was dated with the time of its scan, so a library's first scan dated all its items within microseconds of each other, in walk order.
- **Date added of items already in a library**: Once after this update, items already in a library get their file's date, the one a scan now gives a new item, unless they have an earlier one. An item whose file or folder can't be read keeps its date. This runs once, in the background from the first start; the Date added sort, the recently added lists and item details show the new dates without a restart. Before, these items kept the time of the scan that added them.
- **New administrators**: `POST /Users/New` honors `IsAdministrator`, and a user created in the dashboard with the Administrator box ticked is an administrator. Before, the server ignored the field and the web client dropped the box, so every new user was created without administrator rights.
- **Played and favorite marks of another user**: `POST` and `DELETE /Users/{userId}/PlayedItems/{itemId}` and `/Users/{userId}/FavoriteItems/{itemId}` act on `{userId}`. Before, they ignored it and changed the caller's own marks. An administrator can set them for any user; other users get 403 for anyone but themselves.

The setup wizard creates the first administrator, the server owner, with the typed name and password. Before, the wizard only changed the default admin's password, ignored the typed name and hid sign-in failures. The `/Startup/*` endpoints also stayed anonymous, so anyone could reset the administrator's password. Now:
  - `POST /Startup/User` creates the owner only on a server without users and never changes an existing account. The `/Startup/*` endpoints are open only while the server has no users and need an administrator afterwards.
  - `StartupWizardCompleted` means that the server has users.
  - The owner cannot be deleted or demoted.

  - The wizard shows every failed step and resumes there on retry.
  - `start.sh smoke` creates a throwaway owner in a temporary data directory.
- **Library folders**: Creating a library now checks its folders. Before, `POST /Library/VirtualFolders` stored any path, so the setup wizard and the library dialog accepted a folder that does not exist, and the library's scan found nothing. Now each path must be a full path to a folder that exists on the server and that the server can list. Otherwise the server stores nothing and answers 400 with a message that names each bad path and the reason, for example `The folder "/media/films" was not found on the server.` In Docker, the paths are the ones inside the container.
- **TMDb client**: All TMDb requests share one client with rate limiting (about 9 per second, 4 in flight), retries with backoff, `Retry-After` handling for 429 and the `Rustyfin/<version>` User-Agent. The API key no longer appears in logs or errors. New variables `RUSTYFIN_TMDB_API_KEY`, `RUSTYFIN_TMDB_BASE_URL` and `RUSTYFIN_TMDB_IMAGE_BASE_URL`; the env key takes precedence over the config key and is never shown in or saved to the server configuration.
- **Titles with quotes in the web client**: Play buttons, the sidebar Scan button and other actions now work for titles and library names with an apostrophe, such as *World's Greatest Dad*. The web client built inline `onclick` JavaScript from server values without escaping `'`, so the click failed with a syntax error, and a crafted file name could run script in the page. Actions now read their values from `data-*` attributes through one delegated click handler, and server text is escaped.
- **Resume playback**: Closing the player keeps the position, and playing again resumes there, as in Jellyfin. Before, the web player reported position 0 at start and when it closed, which erased the resume point, and it always started at 0. The detail page offers Resume and Play from beginning; a point in the last 10 % of the runtime counts as watched.
- **Scan progress in the web client**: The scan progress connection now opens. The client used the wrong path (`/websocket` instead of `/socket`), sent no token and read the wrong fields, so the scan banner and the refresh after a scan never worked, and it retried about every second without logging anything. It now refreshes the open view when a scan ends, logs one warning per outage, retries with backoff up to 30 s and closes on logout.
- **Scan and Stop errors**: Every Scan button and Scan All now show an error toast when the scan can't start, for example "library not found". The task Stop button sent no request (`this.delete is not a function`); it now sends it and shows the server's error, for example when the task has already finished.
- **Setup wizard library scan**: The library created in the setup wizard is scanned right away. Before, it stayed empty until the next scheduled scan, up to 12 hours later.
- **Symlinked folders in the folder picker**: `GET /Library/BrowseDirectories` now lists a symlink that points to a folder, under the link's own path, since the library scan follows such links too. Before, the library dialog's folder picker left these folders out, so they could only be typed.
- **Scan notice in the web client**: Starting a scan now shows one toast as the request is sent, and the scan banner is gone. Before, the banner showed alongside the toast, and the toast came only when the scan had ended, since the scan request answers then. The setup wizard now also shows a toast when it starts its scan. A scan that can't start, for example for a deleted library, shows only the error, and one that fails later shows "Scan failed".
- **Scan finished notice in the web client**: When a library scan ends, the web client now shows a toast that names the library, such as "Scan finished: Films", in every open tab, whoever started the scan. Scan All shows one for each library. A failed scan shows only its error. Scans the server runs on its own schedule don't show it yet, since they send no scan events.
- **Resume or start over**: Starting a video that has a resume point from a card, the home page's Play button or an episode now asks whether to resume from the saved time or to start from the beginning, as in Jellyfin. Before, only the detail page offered the choice, and everything else resumed without asking. Escape or a click outside the menu cancels. A video without a resume point, or one in its last 10 %, starts at once.
- **Folder picker in the library dialog**: The picker now works like Jellyfin's. It shows the open folder's path in a field you can edit, where Enter opens the typed folder; a click on a folder opens it; and "Select this folder" adds the open folder to the library's paths. "Create library" also takes the folder the open picker shows, so browsing to a folder and pressing Create works. Before, the picker hid the path field, only a small ✓ next to each folder added a path and the open folder could not be chosen, so Create failed with "Name and at least one path are required".
- **Password hashing no longer blocks the server (M-15)**: argon2 hashing and verification run on a blocking thread pool, so a burst of logins no longer stalls unrelated requests.
- **Login response reflects the current login (M-16)**: `AuthenticateByName` now returns the user with the `LastLoginDate` set by that login, not the previous one.
- **Next Up and Upcoming parameters**: `GET /Shows/NextUp` and `GET /Shows/Upcoming` accept `Limit`, `StartIndex`, `UserId`, `SeriesId` and `ParentId` as well as their camelCase forms, as Jellyfin does. Before, the capitalized forms were ignored, so the web client's Next Up row asked for 12 episodes and got up to 20.
- **Next Up lists one episode per series**: `GET /Shows/NextUp`, and so the home page's Next Up row, lists one episode for each series the user has started: the first unplayed episode after the highest one they have played, as in Jellyfin. The series whose latest episode they watched most recently comes first. `Limit`, `StartIndex` and `TotalRecordCount` count series, and `SeriesId` gives that series' next episode, started or not. Specials (season 0) are left out, since Rustyfin has no data to place them within seasons. With the API key and no `userId`, the list is empty unless `SeriesId` names a series. Before, Next Up listed every episode the user hadn't marked played, across all series, including specials and series they had never started.
- **Intro and outro detection**: Detection now stores its segments. ffmpeg's arguments were built as one string and split on whitespace, so a path with a space or a quote reached ffmpeg in pieces, and every run then failed on two columns that no migration creates. Each argument is now passed on its own, and a new run replaces the item's earlier intro and outro segments.
- **NAS folders and symlink loops in library scans**: Scans skip folders whose name starts with a dot or `@` (QNAP `.@__thumb`, Synology `@eaDir`), `#recycle`, `lost+found` and sample files, following Jellyfin's ignore rules. Before, the thumbnail videos in `.@__thumb` were imported as movies. A symlink that points back up the tree is no longer followed down to the kernel's limit, and the next scan removes the items an earlier scan made from such paths.
- **Episode and season numbers**: Episodes get their numbers from their file names, so they sort by number instead of by name. Scans read `S01E02`, `s1e2`, `S01.E02`, `S01 E02`, `1x02`, `ep05` and `Episode 7`, and the first episode of multi-episode names like `S01E02E03` or `S01E02-E03`; a resolution such as 1080p or a year is not taken for an episode or season. A file directly in a series folder goes to the season its name gives instead of always Season 1.
- **Movie titles**: Movie titles no longer keep the year and release tags of the file name. Scans clean the name with Jellyfin's rules and store the year as the movie's year. Existing movies are renamed on the next scan, unless metadata set the title.
- **Movie versions**: The files of one film in a folder, such as a 1080p and a 2160p copy, are now one movie with a source for each file: the file named like the folder first, then the highest resolution. A file that can't be probed, such as an empty one, is left out until it changes. Before, a fresh scan made a movie per file, and every rescan added the alternate files as sources again. The next scan merges an existing library's copies into one movie and keeps their watch history, favorites, collections and playlists. The runtime and chapters come from the first source; an alternate no longer overwrites them.
- **Concurrent scans**: Scans run one at a time, so two scans started together, such as a manual scan during the scheduled one, no longer create the same movie twice.
- **Episode versions**: The files of one episode in a season, such as a 1080p and a 2160p copy, are now one episode with a source for each file, the highest resolution first. A file that can't be probed, such as an empty one, is left out until it changes. Before, every file was an episode of its own. The next scan merges an existing library's copies into one episode and keeps their watch history, favorites and playlists. A file directly in a series folder joins the same episode in its season's folder.
- **Playing other versions**: Playback now uses the version that `MediaSourceId` names. `GET` and `HEAD /Videos/{id}/stream` and `/Videos/{id}/stream.{container}`, `progressive.stream` and the HLS transcode (`main.m3u8`) read that version's file. `/Videos/{id}/Universal` and `/Videos/{id}/PlaybackInfo` offer that version, and Universal's direct play, direct stream and transcode URLs name it. No id, or the item's own id, plays the first version as before; an id that names no version of the item gets 404. A transcode of one version is never reused for another. Before, every route played the first version whatever the id, and `/Videos/{id}/stream.{container}` answered 500.
- **Unsatisfiable byte ranges**: `GET /Videos/{id}/stream` and `/Audio/{id}/stream` answer a range that starts past the end of the file, or `bytes=-0`, with 416 and `Content-Range: bytes */<size>`. Before, `bytes=-0` crashed the request and a start past the end returned the whole file with 200.
- **Transcodes stalled after a few minutes**: the server now reads ffmpeg's log output as it comes. Before, ffmpeg blocked once its unread log filled the pipe, so playback stopped after a few minutes and the player waited for segments that never came.
- **Two viewers of one video**: each play session gets its own transcode, so a second viewer no longer replaces the first one's stream. `DELETE /Videos/{id}/Transcode?PlaySessionId=` stops only that session, the new `DELETE /Videos/ActiveEncodings?playSessionId=&deviceId=` stops a session's transcodes, and idle transcodes stop 30 minutes after their last request instead of an hour after they started.
- **Transcode errors**: when ffmpeg fails, `GET /Videos/{id}/main.m3u8` answers 500 with ffmpeg's last log lines instead of "Cannot read playlist", and when ffmpeg has written no playlist after 30 seconds it answers 503 with `Retry-After: 5`.
- **Audio-only transcodes**: `AudioOnly=true` no longer passes `-an` to ffmpeg, which dropped the audio and failed every audio-only transcode.
- **Direct stream of codecs the client can't play**: `GET /Videos/{id}/Universal` and `/Videos/{id}/PlaybackInfo` now check the source's codecs against the client's `VideoCodecs` and `AudioCodecs` for direct stream too, not only for direct play, and send the rest to the transcoder with the response's `PlaySessionId`. A client that sends no lists is assumed to play H.264 video with AAC or MP3 audio; before, HEVC, VP8, VP9, Opus and AC3 counted as playable everywhere.
- **Direct play of scanned videos**: `GET /Videos/{id}/Universal` and `/Videos/{id}/PlaybackInfo` now recognise the stream types the scanner stores (`video`, `audio`), so a scanned MP4 with H.264 and AAC is direct-played. Before, the checks looked only for `Video` and `Audio`, so every scanned video was offered as a transcode and the codec checks never ran.
- **HLS transcodes failed**: `GET /Videos/{id}/main.m3u8` now always encodes H.264 video and AAC audio, and copies the video, or AAC audio, as it is when the client plays it, so an H.264 movie with AC3 audio keeps its picture and gets stereo AAC sound. Before, the client's codec lists reached ffmpeg as encoder names and the transcode failed. Segment lines now point at `/Videos/{id}/hls/{playbackId}/video/` and carry the playlist request's query, `api_key` included, so the player can fetch them.
- **Web player ignored the server's playback choice**: the web client now asks the browser which video and audio codecs it plays, sends those lists to `/Videos/{id}/Universal`, and plays the URL the server returns. Before, it claimed AC3 and HEVC everywhere and always played the raw file, so a movie with AC3 audio played without sound in Chrome.
- **Transcoded videos in Chrome**: The web client now loads hls.js, so the player plays HLS transcodes through hls.js in every browser that supports it, and uses the browser's own HLS playback only as a fallback. Before, the build shipped hls.js, but no page loaded it, so Chrome played transcodes with its own HLS player, which treated a running transcode's growing playlist as a live stream and stopped after a few seconds with `DEMUXER_ERROR_COULD_NOT_PARSE`.
- **Scan progress next to library names**: While a library scans, a ring next to its name in the sidebar, on the home page's My Media cards, in the library page title and in the admin Libraries tab fills with the scan's percent, spins while the percent isn't known yet, shows as a dashed circle while the scan waits for another scan to finish, and goes away when the scan ends. It shows for every scan, including the scheduler's and those started in another browser or by another user, and it survives a reload or reconnect. Before, an amber dot showed only in the sidebar and on the home cards, only for scans this browser had seen start and only once the page was redrawn, and it went away before the scan's probes had finished.
- **Scan All's reload and completion**: Scan All clears the server's caches after each library's scan, before it sends that library's `LibraryChanged`, so the page that reloads on that event shows the new items. Before, it cleared them only after the last library, so the reload could show stale lists. Its `ScheduledTaskCompleted` for all libraries now comes after every library's scan has ended, probes included, instead of when the last scan returned.
- **Music scan progress and artists**: A music library's scan counts the files of all its folders before it reads the first one. With a metadata provider configured, it also counts each new artist, album and track, so its percent rises steadily and reaches 99 only when the scan ends. Before, a library with two folders showed 99 % while the second folder was scanned. A rescan that finds a new album in a known artist's folder adds it under that artist. Before, it added a second artist with the same name.
- **Replaced and deleted files**: Every scan probes a known movie, episode or music track again when its file's size or modification time differs from the one stored with its source, so a replaced file gets its new runtime and streams; a movie or episode with versions has all of them probed again. A file that replaces a missing one under another name, as a Radarr, Sonarr or Lidarr upgrade or rename does, takes over the missing file's item: a movie in the same folder with the same title and year, an episode with the same season and episode number in the same show, in any of its season folders (as when Sonarr's season folder format changes from `Season 1` to `Season 01`), or a track with the same track number and title in the same album folder. For this match, an episode's season is the one in its file name, else its folder's, so a special such as `S00E01` in a season folder and that season's episode 1 each keep their own item. The item keeps its id, its users' played state and favorites, and its metadata, and its new file is probed. When a file matches several missing items, such as two copies of one episode, the oldest takes it, and the others merge into it with their users' data. Trailers and samples, by Jellyfin's names for them (such as `-trailer` and `_sample`), take over no item. A file that the scan lists but cannot read keeps its streams. Sources store this stamp after each probe, and sources from an older build get theirs at their first scan, without a probe. Every scan, of music libraries too, also removes the items whose file is gone, and then the seasons, series, albums and artists left without children. A symlink whose target is missing, as when an rclone or debrid mount drops, keeps its item and its users' data until the link itself is removed, and the scan logs one warning per folder that holds such links. Under a library folder that is missing, or lists nothing that the scan doesn't ignore other than such links, such as an unmounted share, it removes nothing and logs one warning for that folder. Before, a replaced file kept its old runtime and streams, a scan kept the items of deleted files, and music scans removed nothing.
- **10-bit and 4:2:2 video in browsers**: Transcodes encode H.264 as 8-bit 4:2:0 (`format=yuv420p`, or `format=nv12` on the VAAPI, CUDA and QSV scalers), whatever the source's depth and chroma, and with burned-in subtitles too. `GET /Videos/{id}/PlaybackInfo` and `GET /Videos/{id}/Universal` no longer direct play or direct stream 10-bit, 4:2:2 or 4:4:4 H.264, unless the request says the client takes it with Jellyfin's `Profile`, `h264-profile`, `MaxVideoBitDepth` or `h264-videobitdepth` (Jellyfin's rules). The same statement now lets HLS copy such video, which it always encoded before. When no bit depth is stored, a profile name with "10" counts as 10-bit. Before, x265 Main 10, Hi10P and 10-bit AV1 files came out of a transcode as 10-bit H.264, and a High 10 or High 4:2:2 MP4 was sent as it is: browsers decode neither, so they failed in the web player. HDR10 files play, but they aren't tone-mapped: the 8-bit stream keeps its PQ and BT.2020 tags, and Chrome maps it to SDR itself, so it looks darker than a tone-mapped transcode would.
- **Search by item type**: `/Search` finds the items of the types named in `IncludeItemTypes`, and without that parameter searches movies, series, episodes and audio. Before, it answered 500 unless `IncludeItemTypes` named no type it knew, because its query bound the types and the limit to the wrong parameters and compared the stored types with quoted names.
- **Cached search answers**: `/Search` reuses a cached answer only for a request with the same term, item types, start index and limit, and `/Search/Hints` only for the same term and limit. Type names in `IncludeItemTypes` match in any case, as in Jellyfin. Before, terms that differ only in the case of a letter outside ASCII, such as `Été-` and `été-`, shared one answer although they can find different items.
- **Repeated searches**: `/Search` sends a cached answer exactly as it first sent it. Before, the cache served an answer again only when it held no movie or episode, and changed its items: series came back as folders (`"Type":"Folder"`, `"IsFolder":false`), and items lost their run times.
- **Search as in Jellyfin**: `GET /Search/Hints` and `GET /Search` read parameter names in any case, and kind, media type and boolean values without case, as Jellyfin does. Before, both read only PascalCase names, so `searchTerm`, the name in Jellyfin's API, found nothing.
  - `/Search/Hints` applies Jellyfin's parameters: `IncludeItemTypes`, `ExcludeItemTypes`, `MediaTypes`, `ParentId`, `StartIndex`, the `Include*` flags (people, media, genres, studios, artists), and `IsMovie`, `IsSeries`, `IsNews`, `IsKids` and `IsSports`; the last three match the item tags `News`, `Kids` and `Sports`. It never lists folders, years or collection folders, orders as Jellyfin does (the same name first, then names that start with the term, then names with a word that starts with it, then the rest), and pages after counting, so `TotalRecordCount` counts every match. Without `Limit` it lists 100 hints. A missing or blank `SearchTerm`, a negative or too large count, and a bad id or boolean get 400, and a `UserId` other than the caller's gets 403 unless the caller is an administrator. Before, it applied only the term and `Limit` (default 20), and `TotalRecordCount` was the page's length.
  - Hints carry `ItemId`, `Artists` and Jellyfin's `MediaType` (`Video`, `Audio`, ...), without which Jellyfin's Kotlin SDK can't read them, and the fields Jellyfin fills where Rustyfin has the data: index numbers, image tags and aspect ratio, `IsFolder`, `Series`, `Status`, `EndDate`, `Album`, `AlbumId` and `AlbumArtist`. Before, `MediaType` held the item's kind.
  - `/Search` reads `Term`, else `SearchTerm`, and knows every kind Rustyfin stores. A list that names no kind it knows counts as no list: movies, series, episodes and audio. A negative or too large `StartIndex` or `Limit` gets 400. Before, such a list searched every kind, folders included, and a negative count was read as a huge number.
  - Both trim the term and key their cached answers by every parameter they apply, under new keys, so no answer cached before is served.
  - The web client's search page shows its no-results message for a blank term without asking the server.
- **Watch data in item details**: `GET /Items/{id}` shows each user their own `UserData` (played state, play count, favorite, resume point, last played date) and `CompletionPercentage`, and a change to them shows on the next request. Before, the details of a track, album, photo, series, season or genre were cached for 5 minutes with the first viewer's watch data in them, so every other user got that user's played state, favorite and resume point, and a change showed only when the entry expired. A cached answer also came back changed: a series, season or genre as a folder (`"Type":"Folder"`, `"IsFolder":false`), an album as `"Audio"`, and items without their run times.
- **Resized images of different paths**: an image asked for at a smaller size is resized from its own file. Before, two images at different paths, such as the posters in the folders `ab` and `bA`, could share one resized copy, so one item showed the other's picture, because the copies were named by a short hash of the path. Copies are now named by a SHA-256 of the path, plus the size. Copies under the old names in the data directory's `cache/images` are no longer read and can be deleted.
- **Deleting items with watch data**: `DELETE /Items/{id}` and `DELETE /Items?ParentId=` now delete an item that a user has marked as a favorite or played, has a resume point on or has pinned an episode of, and a series with its seasons and their episodes. Before, such a delete failed with 500, and the many-item delete skipped those items silently. The item, its descendants and every row that refers to them through a key go in one transaction, through the same function the scanner uses to remove items.
- **Deleting users with data**: `DELETE /Users/{id}` and `POST /Users/{id}/Delete` now delete a user who has favorites, played marks, resume points, pinned episodes, playlists, collections or display preferences, together with all of these, their sign-ins and their reset PINs, in one transaction. Before, `POST` failed with 500, and `DELETE` answered 200 but kept the user, who could go on signing in. `DELETE` now answers 204 like Jellyfin, 404 for an unknown user and 400 for the caller's own account (403 for the owner); `POST` still answers 200.
- **More video file types**: Scans pick up the video extensions Jellyfin knows and Rustyfin skipped, such as `.m2ts`, `.mts`, `.vob`, `.ogv`, `.rmvb`, `.3gp` and `.wtv`, but not disc images (`.iso`, `.img`, `.nrg`), `.ifo`, `.strm`, `.asx` or `.001`. A `.bin` file counts only in TV libraries, and only when its name reads as an episode, such as `Show.S09E10.bin`. `BDMV` and `VIDEO_TS` folders are skipped, so the streams of a Blu-ray or DVD folder don't become movies or episodes of their own. Of a movie's versions without a resolution in their names, the one whose name sorts first without its extension plays by default, as in Jellyfin, so `Big Eyes.mkv` stays ahead of `Big Eyes (2014) BR-DISK.m2ts`.
- **Episode numbers like `Name.E02.`**: TV scans read the episode number from file names such as `Dekalog.E02.1989.720p.mkv`, as Jellyfin does, and the next scan sets it on episodes stored without one. The rule comes before the `1x02` and `Episode 7` rules, as in Jellyfin, so the next scan also renumbers a stored episode whose name both rules match.
- **Specials folders**: A season folder named `Specials` in any case, such as `SPECIALS` or `[Specials]`, or with the series folder's name in it, such as `Show - Specials` or `Show Extras`, is season 0, as in Jellyfin. A folder named just `Extras` is season 0 too, where Jellyfin shows its videos as the series' extras. An episode whose file name gives another season, such as `Show S01E05.mkv`, keeps that season, as in Jellyfin. The next scan sets season 0 on such seasons stored without a number, and on their episodes whose file names give no other season.
- **Series named `Name (Year)`**: A series folder such as `One Night (2023)` gives the series the name `One Night` and the year 2023, as in Jellyfin. The next scan renames series stored under the folder's name, and gives the year to those with none; a name that isn't the folder's is kept.
- **tvshow.nfo**: A series reads the `tvshow.nfo` inside its folder, as in Jellyfin. Before, the series never read it, and its seasons, and episodes beside the file, took its plot, year, ratings, genres and runtime instead, and sometimes its title. The next scan fills the series' empty fields from the file and clears from its seasons, and from the episode files beside it with no `.nfo` of their own, what they took. Such an episode that took the show's title gets its file name back, and the file's images are removed from the seasons and those episodes.
- **Multi-episode files**: An episode file such as `Show S01E03-E04.mkv` keeps its last episode too, and items return it as `IndexNumberEnd`, as in Jellyfin; before, only the first episode was stored. The next scan gives it to episodes already in a library.
- **Seasons with no folder**: A season made for episode files that sit in the series folder itself has no `Path` and the `LocationType` `Virtual` in items, as in Jellyfin; before, it had a made-up path such as `…/Show/Season 1` that no folder had. It keeps its id. The next scan corrects seasons already in a library, and gives a season its path back once its folder exists.
- **Image sizes**: `maxWidth` and `maxHeight` never enlarge an image, and each side is capped at 4096 pixels; a request at or above the image's own size gets the original file, and requests that come to one size share one copy. Only JPEG, PNG, GIF, WebP and BMP files are sent as they are, and a request with bounds gets a copy of a file over 8 MiB; other formats, such as TIFF, always come back as a JPEG copy. Before, any size was rendered, `maxWidth=40000` included, which could exhaust the server's memory.
- **Image memory**: decoding refuses images over 16384 pixels a side or that would take over 256 MiB, at most two images are resized at once, off the request threads, and a large shrink goes in two steps, so a copy takes a bounded amount of memory. Remote images over 20 MiB are refused, and originals over 1 MiB are streamed from their file. Image sizes are read from the start of the file. Before, an 8000x8000 poster resized to 4096 pixels needed a 500 MB buffer per request, and a TIFF at full size was sent as is, labelled as a JPEG.
- **Replaced images**: an uploaded image, or a poster replaced on disk and found by a scan, shows at once in apps that send the image tag, the Rustyfin web client included, and within five minutes in other apps: an image requested with a `tag` may be cached for a day, one without for five minutes. The image tag, the server's in-memory key and the names of resized copies carry a stamp of the file's size and modification time (stored by migration 070), and an upload clears the item's cached answers. `/Search/Hints` and people's `PrimaryImageTag` use the same tags. Before, the tag was a constant such as `Primary_0`, so clients and the server kept the old picture. A library scan, a scheduled one included, also clears cached item details, which kept old values for up to 5 minutes, and stores the new stamps of a library's images in one transaction.
- **Series images on episodes**: an episode carries its series' `SeriesPrimaryImageTag` in its own details and in lists, and the details of an episode, season, track or other child carry its parent's and series' image tags. Before, details read the parent without its images and lists never read an episode's series, so these were left out and clients showed no series poster for an episode.
- **Resized image files**: a resized copy is written under a temporary name and renamed into place, and an empty or cut-short copy is made again. Before, a crash or two first requests at once could leave a truncated copy that was served from then on. The six-hourly cache cleanup, which also runs at startup, deletes files in `cache/images` that are not current copies (older name formats included) and temporary files over an hour old, then trims the copies to 1 GiB, least recently used first. It also runs after every 64 MiB of new copies, a file it can't delete is logged and skipped, and a temporary file dated in the future counts as old. Before, nothing there was ever deleted.
- **Search paging**: `/Search` answers 400 for a `StartIndex` or `Limit` below 0 or above 2147483647. Before, `Limit=-1` returned every match and `StartIndex=-1` overflowed, a panic in debug builds. `/Items` reads a negative `StartIndex` as 0 and answers with the `StartIndex` it was sent, as Jellyfin does, and reads a negative `Limit` as the default limit. `/Items/{id}/Similar` reads a negative `Limit` as none, so it lists 12 items; before, `Limit=-1` listed every similar item.
- **Search index errors**: search falls back to matching names only when the search index can't parse the term, such as `Star Trek: Discovery` or `Mr. Robot`. Any other index error answers 500 and is not cached. Before, a missing or broken index gave a narrower answer from names alone, and that answer was cached.

### Security
- **Administrator endpoints**: Endpoints that change the server or show its internals need an administrator, following Jellyfin's rule for each endpoint. They cover configuration changes, shutdown and restart, logs, scheduled tasks, plugins, packages, backups, devices, the activity log and API keys. They also cover creating and deleting users and setting their policy, library and item refreshes, deleting items, uploading and deleting images, subtitle management, collections, Live TV tuners and listing providers, DLNA profiles, localization providers and the media encoder settings. Before, any signed-in user could call them, and the DLNA profile endpoints needed no sign-in. A request without a valid token gets 401; a signed-in user without the right gets 403, which also replaces the 401 for another user's account settings.
- **Library setup endpoints**: `/Environment/Drives`, `/Environment/NetworkShares`, `/Library/BrowseDirectories`, `/Library/VirtualFolders` and `/Library/{id}/Options` are open only while the server has no users, and need an administrator afterwards, as in Jellyfin. Before, the Environment endpoints listed the server's drives to anyone without a sign-in, and every user could browse the server's folders and change the libraries.
- **Files outside their folders**: `GET /System/Log/{name}` returns only a log file that `GET /System/Logs` lists, and the HLS segment endpoints return only a segment in the item's transcode folder. Other names get 404. Before, a signed-in user could read any file the server could read, with a name such as `..%2Fconfig.json` or `%2Fetc%2Fhostname`.
- **Media encoder path**: `PUT /System/MediaEncoder/Path` and `POST /System/MediaEncoder/Path/Validate` are removed. They ran the program at the path in the request, so any signed-in user could run any program on the server. As in Jellyfin, the encoder path cannot be changed through the API. `POST /System/MediaEncoder/Test` stops FFmpeg after 10 seconds.
- **Easy PIN**: `POST /Users/{userId}/EasyPassword` stores the PIN as an Argon2 hash, and no response returns it. Before, it replaced the user's configuration with the PIN in plain text, and `GET /Users` showed it to every user. The upgrade removes PINs stored the old way; set them again.
- **Configuration secrets**: For users who are not administrators, `GET /System/Configuration` and `GET /System/Configuration/{key}` return `TmdbApiKey`, `OmdbApiKey`, `FanartApiKey` and `SmtpPassword` as null. Before, every signed-in user could read them.
- **Empty API key and secret**: An empty `RUSTYFIN_API_KEY` (for example `RUSTYFIN_API_KEY=` in compose or an empty field in a NAS template) gave administrator access to any request with an empty token, such as `?api_key=`. An empty `RUSTYFIN_SECRET` let anyone sign their own administrator tokens. `RUSTYFIN_API_KEY` is now trimmed, an empty value counts as unset, and the server logs a warning. `RUSTYFIN_SECRET` is no longer used, since access tokens are stored server-side. An empty token never authenticates. The `/socket` websocket now also accepts user tokens when an API key is set, so the web client's scan progress works on such servers. The docs use placeholders instead of example keys.
- **Another user's watch data**: `GET /Users/{userId}/Items/Resume`, `GET /Notifications/{userId}` and `DELETE /Users/{userId}/Items/{itemId}/Rating` need the caller to be `{userId}` or an administrator, and so does a `userId` given to `GET /Shows/NextUp` and `GET /Shows/Upcoming`. Other users get 403; an administrator naming an unknown user gets 404. Before, any signed-in user could read another user's resume list, Next Up, Upcoming and notifications, and clear their ratings. Without `userId`, Next Up and Upcoming now follow the caller's own watch history, as in Jellyfin; before, they ignored it and also listed episodes the caller had already watched.
- **Remote control of other users' sessions**: `POST /Sessions/{sessionId}/Command`, `/Sessions/{sessionId}/Command/{command}`, `/Sessions/{sessionId}/Message` and `/Devices/{deviceId}/Command` need the caller to own the session or device, or to be an administrator. Other users get 403, also for an id that does not exist; an administrator gets 404 for one. `GET /Sessions` lists only the caller's own sessions unless the caller is an administrator. Before, any signed-in user could send commands and messages to everyone's sessions and see every session on the server.
- **LAN admin takeover via the reset PIN (R1-01)**: The forgot-password flow now follows Jellyfin's. A reset PIN is issued only to a request from the local network and only for an existing user, written to a file in the data directory (mode 0600), and never returned or logged; the response is uniform, arrives after the same fixed delay (250 ms), and does not reveal whether a user exists. The PIN is random, stored only as a hash, valid for 30 minutes, single-use, and voided after five wrong attempts. The old biased PIN generator was removed (M-17).
- **Access tokens can be revoked (R1-08, R1-09)**: Logging out ends that device's token, changing a password ends the user's other tokens, and deleting a user ends all of theirs; a disabled user's existing tokens are rejected. Restarts keep valid tokens valid.
- **`admin`/`admin` after an upgrade**: At startup the server logs a warning naming any enabled administrator whose password is still `admin`.
- **Setup wizard on upgraded servers**: At the first start after an upgrade, a server that has users but no owner makes its earliest enabled administrator the owner, logs it and marks the setup wizard complete in `config.json`, even if the wizard was never finished. If no administrator is enabled, the server logs an error with the steps to make one, and the wizard stays closed. The `/Startup/*` and library setup endpoints are open only while the server has no users, and `POST /Startup/User` never changes an existing account. Before, a server whose wizard was never finished, or that had no enabled administrator, kept no owner, so anyone who could reach it could use the wizard without signing in to set a new password on any account and make it an administrator and the owner.
- **Proxy address handling**: `X-Forwarded-For` is read across all header lines, right to left, with `ip:port` and `[v6]:port` entries; loopback is trusted as a proxy only when listed in `RUSTYFIN_KNOWN_PROXIES`, and a malformed entry no longer resolves to a client-chosen address. The reset-PIN LAN check uses the same client address, IPv4-mapped IPv6 peers count as their IPv4 address, and IPv6 clients share one login budget per /56, so a site can't get more budgets by moving through its /64 subnets. A peer that is not listed but sends `X-Forwarded-For`, `X-Real-IP` or `Forwarded` is neither local nor exempt from the login limit, and all its clients share one budget. Before, a client behind a same-host proxy could claim the loopback exemption.
- **Reset PIN guessing bound**: a new forgot-password request no longer replaces a pending or voided reset, so each reset allows at most 5 wrong PINs; redemption is atomic and deletes the PIN. `ResetPassword` answers an unknown user like a wrong PIN.
- **Sessions end on device removal**: removing a device (`DELETE /Devices?id=` or `DELETE /Devices/{deviceId}`) signs it out.
- **Revoked sessions close their websocket**: an open websocket closes within about 5 seconds after its token is revoked, also when it is revoked while the socket opens.
- **Continue Watching, favorites and watched filters**: `GET /Items/Resume` lists only the caller's part-watched items, each once, and accepts `userId` under the same rules as Next Up; the API key without `userId` gets 404, as in Jellyfin. `IsFavorite`, `IsPlayed` and `IsUnplayed` match only the caller's favorites and watch history. Before, Continue Watching showed every user's items, an item two users had started appeared twice, and the filters matched any user's data. The last item of every list, and the only item of a one-item list, now carries the caller's `UserData`; before, it had none.
- **Cached library list queries**: a list request such as `/Items` reuses a cached query only when it has exactly the same shape: the same filters with the same number of values each, and the same sort. Before, a signed-in user could send a request the server mistook for a different cached one; the answer could then list another user's favorites or watched items, or a library view could answer 500 for every user until the server restarted.
- **Live updates over `/socket`**: A user who is not an administrator now gets only their own session and playback events (`SessionChanged`, `PlaybackStart`, `PlaybackProgress`, `PlaybackStop`) and no server log lines (`LogMessage`); administrators and the API key still get every event. Remote-control commands and messages to a session or device now name its owner, so they reach that user and administrators only. Authorizing a Quick Connect code no longer sends the code's secret to every socket. Before, every signed-in user's socket received all users' session and playback events and the server's log lines.
- **Other users' playlists**: The playlist routes (`/Playlists/{id}`, its `Items` and its `Users`) answer only the playlist's owner and administrators. Anyone else gets 404, as for an unknown id, so an id no longer lets a user read, rename, edit or delete another user's playlist. Deleting an unknown playlist now answers 404 instead of 204.
- **Cached answers after sign-out**: The web client forgets its cached API answers when a user signs out or signs in, so the next user on the same tab no longer sees the previous user's Continue Watching, Next Up, favorites or played state. An answer still loading at sign-out isn't cached either.
  - A page still loading at sign-out is no longer drawn over the signed-out page, and a late 401 for the previous session no longer signs out the next user. A session that ends with a 401 now also clears the name in the header. Signing out drops the import page's setup codes and the server log lines the page held, the setup wizard forgets the first administrator's password once it has signed in, and a tab reloads when another tab signs in or out.
- **Another user's now playing item and ratings**: `GET /Sessions/Playing/NowPlayingItem?SessionId=` needs the caller to own the session or to be an administrator. Other users get 403, also for a session that does not exist; an administrator gets 404 for one. `PUT /Users/{userId}/Items/{itemId}/Rating` sets `{userId}`'s rating and needs the caller to be `{userId}` or an administrator; other users get 403 and an administrator naming an unknown user gets 404. `DELETE` on the same path answers 404 for an unknown item. Before, any signed-in user could see what another user's session was playing, and setting a rating ignored `{userId}` and always changed the caller's own rating.
- **Quick Connect codes**: `POST /QuickConnect/Initiate` counts toward the sign-in rate limit, and the server keeps at most 100 pending requests, and 5 for each client address or IPv6 /56, loopback included (429 beyond that). A code is unique among pending requests, and `POST /QuickConnect/Authorize` approves only a pending request that hasn't expired. A code there that matches no pending request counts toward the sign-in rate limit, and a client over that limit gets 429 at Authorize too. Before, anyone could start unlimited requests, codes could repeat, and an approval could go to an expired request or to another device's request with the same code.
- **Query strings in the request log**: At debug level, request log lines name the method, the path and the HTTP version, without the query string. Before, they showed the whole URL, including `api_key` tokens and the `code` and `state` of an OIDC callback.
- **Long user names**: A user name is at most 255 UTF-16 code units, as in Jellyfin. `POST /Users/New`, `PUT /Users/{userId}` and `POST /Startup/User` refuse a longer name with 400. Before, a name of any length was accepted. An account from before the limit keeps its name and still signs in with its exact name.
